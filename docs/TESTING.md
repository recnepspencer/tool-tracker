# Regression evidence

Run `npm run check` for TypeScript, page-boundary lint rules, formatting, HTTP-client boundary checks, and the production PWA build. Run `npm run test:browser` with PostgreSQL and installed backend dependencies available. The launcher reads `backend/.env` locally and preserves existing environment values in CI. It creates a disposable database per browser test file, applies normal migrations, starts a separate API on port 8002 and an audit worker, and proxies the production preview on port 4173 to that API. These two ports must be available. Each file has its own inbox, media directory and diagnostics under `artifacts/browser-runs/`; owned processes and databases are cleaned up after success or failure. The live review API/database remain independent. Use `npm run test:browser -- e2e/custody-recovery.spec.ts -g warehouse` for a focused run. Authentication throttling remains enabled.

Browser scenarios create isolated companies through public HTTP endpoints and use actual sessions, CSRF, file-inbox email, PostgreSQL, and private photo downloads. No business endpoint is mocked. Account scenarios prove verified signup, invitation switching, recovery, replay prevention, and offline behavior. Workspace scenarios prove separate physical units, URL navigation, condition/service/lifecycle independence, stale-edit recovery, company isolation, configurable participation and employee registration, suspension, and photo authorization. Small shared setup helpers use the same public API; the scenario assertions inspect the UI and persisted outcomes rather than helper call sequences.

The isolated runtime uses local development cookie settings and a file-based email backend even if SMTP is configured in the developer's environment. It never sends test messages through a production email provider. Authentication, authorization, CSRF, throttling and credential revocation still run through their ordinary application paths.

The backend gate is `python scripts/check_api.py` from `backend/` using the configured environment. It checks declarations, migrations, PostgreSQL constraints, OpenAPI drift, populated upgrades, behavior, lint, and formatting. Fixtures remain domain-owned. The seeder is separately tested for repeatability and preservation of user changes.

The removed demo tests exercised a retired mock implementation. They remain in Git history, and are not counted as evidence for the API-backed application. CI runs the same real PostgreSQL and production-browser gates before packaging the web application.

`e2e/demo-parity.spec.ts` adds real photographed inventory, accepted and pending handoffs, mobile sheet navigation, queue filters, and selected visual measurements from the original demo. Its screenshots are `artifacts/parity-*.png`. These checks establish specific behavior and layout evidence; they do not establish whole-app visual parity. See [the parity checklist](DEMO_PARITY.md) for remaining acceptance work.

`e2e/role-surfaces.spec.ts` exercises allowed and denied routes, desktop/mobile navigation, and selected capability controls for all five company roles, a scoped warehouse manager, a foreman assignment, and combined dispatcher/equipment roles. It records unexpected HTTP failures and browser errors. These are route/access checks, not exhaustive mutation journeys. `e2e/cutover-workflows.spec.ts` covers profile conflicts, warehouse archive/restore and in-use denial, job-filtered custody directory, registration after a committed command loses its response, and actual audit-worker visibility/filtering. CI starts the audit worker as well as the API; a mocked activity feed is not used.

The backend role-boundary suite independently checks public read access and representative mutations for every company role. Supplemental warehouse grants and foreman responsibilities are tested separately. Profile tests cover persisted changes, role and tenant denials, stale revisions, invalid timezones, and a populated pre-address migration. Remaining workflow coverage is tracked in [the cutover audit](CUTOVER_AUDIT.md).

`e2e/catalog-lifecycle.spec.ts` protects shared-model edits, category/model archive and restore, registration eligibility, and revocation of inactive warehouse managers. `e2e/custody-decisions.spec.ts` exercises request decisions for company/equipment/warehouse reviewers and transfer/cancel/return for four holder variants. `e2e/custody-recovery.spec.ts` covers stranded proposals, named former holders, evidenced correction, receiving-warehouse authority changes and custody preservation on denial. Photographed handoff retries execute a real command and then lose its response, proving that staged evidence and command identity survive retry.

Tool surfaces use persistent parent routes with nested sheets. The parity and workspace journeys check the actual filtered background, checkout list mode, flagged-list return, registration return and keyboard focus restoration, rather than asserting only that the dialog disappeared.

The job/access audit adds independent browser journeys in `e2e/jobs-management.spec.ts`, `e2e/access-lifecycle.spec.ts` and `e2e/workspace-access.spec.ts`. These cover manager roles, direct and reviewed participation, replacement assignments, employment end/reinstatement, live role/grant/policy changes, multiple workspaces and credential changes across tabs/browsers. Onboarding keeps its first-tool receipt and recovery journey; job form interactions belong to the dedicated job journeys rather than making account tests depend on the jobs layout. The pure return-URL validator runs in Node without a DOM; HTTP-client boundary tests retain their browser environment.

Direct participation journeys operate the actual accessible switch, check persisted assignments after reload, and retry a committed command after losing its response. The mixed-policy journey joins by keyboard, verifies the manager-help state for disabled leaving, then requests and receives approval to leave. Registration-policy coverage checks employee navigation, a rule changed during a draft, normal sheet dismissal, manager registration availability and re-enabling employee registration. These follow existing company settings; they do not introduce additional business restrictions.
